# Many-to-many dock links

Status: built on branch `freightdock-networks` (steps 5-9, 2026-11), not yet released; see Next at the end. The released mod (1.1) links freight docks one-to-one; this branch turns its pairs into networks on load. The persistence spike (2026-11-01) is on branch `freightdock-packed-links-spike`.

## Goal

Let freight docks take part in **networks** instead of fixed pairs. Every provider on a network can supply every requester on it, so goods can fan out, fan in and chain across islands.

## Current design (one-to-one)

- **Pairing storage:** the game's own `WorkDock.activeTradePartnerId` (int32), as `-2 - targetDockId`.
  - Paired means a value of -2 or below; `-1` is the game's own "no target".
  - The game never sets values of -2 or below, so its own trade logic ignores them.
- **Persistence:** the field survives the game's `.whisker` save format even though it has no `CPF_SaveGame` flag. The mod adds no save data of its own; all other state is rebuilt on load.
- **Native flags:** each dock's `StockpileLinker` holds two lists the game saves itself, which the mod calls output (the game's "Deliver to", `m_destStockpileIds`) and input (the game's "Pick up from", `m_sourceStockpileIds`). The mod already reads both: the target's output warehouses make the demand (`DeficitsFor`), and this dock's input warehouses cap what is loaded (`BPL_FDLoad.Plan`).
- **Per-dock state:** runtime state in BP_MapLoad is keyed by dock ID and assumes one target per dock:
  - routes: `RoutePts`, `RouteLen`, `RouteCurves`, `PreviewCourses`;
  - voyages: `Voyages`, `VoyageShip`, `VoyageSpline`, `VoyageDist`, `VoyageWait`, `VoyageBerth`, `VoyageTargetId`, `VoyageEndFwd`;
  - loading: `LoadingSince`, `DepartedAt`, `Requested`, `PickupSeen`, `PickupSince`;
  - the target itself comes from `TargetOf`.
- **Code:** graph functions are generated by fdgen (`Tools/FreightDock`); the panel (`UI/WBP_FDPanel.lm` and its rows), the loading plan (`Loom/BPL_FDLoad.lm`) and the unloading animation (`Loom/BP_FDFling.lm`) are written in Loom.

## Persistence spike: result

Question: can one int32 hold several links and still survive a save/load?

- **Test value:** `-(2 + (5 | 7<<6 | 9<<12 | 33<<18 | 62<<24))` = **-1048875463**.
- **Procedure:** `SpikeStorage` (run once, about 2 s after load) wrote the value into an unpaired freight dock (11700); the game was saved and reloaded.
- **Result:** the reloaded dock read back -1048875463 exactly. The existing pair (11769 ↔ 11691) was untouched, route planning ran normally, and nothing in the game reacted to the odd value.
- **Conclusion:** at least 30 bits of payload survive a save, with no extra save data.

Spike leftovers:

- **Code:** `SpikeStorage`, `SpikeTick` and the variable `SpikeFrames`, on the spike branch only (`Tools/FreightDock/fdgen/features/spike.py`); they were left out of the merge. Removal steps are in that file's docstring.
- **Test dock:** the test save's dock 11700 still holds the test value, which the current mod reads as a network value (requests on 5 and 8, both on 17, paused). To clear it, untick its networks in the network GUI.

Other places were tested on 2026-11-04 (see Extra storage): only the profile save's key-value store also survives, and it isn't part of the colony save. 30 bits are enough for the layout below.

## Decided: network membership

A dock stores **which networks it belongs to, and in which role**, never which docks it links to. There is no per-map dock limit and no per-dock link limit. (The earlier slot format, 63 docks with about 4 links each, is dropped; its limits were a large part of why the work was tabled.)

- **Networks:** IDs 1–31.
- **Memberships:** up to 3 per dock, each with its own role: provide, request, or both.
- **Links:** on each network, every provider supplies every requester; a dock never supplies itself.
- **Example:** dock A provides on 1; dock B requests on 1 and provides on 3; dock C requests on 3. The result is a chain, A → B → C.
- **Roles per membership** matter for chains like this one: a single role per dock could not express B.
- **Provide and request on the same network** is allowed. It is today's two-way pairing, and migration relies on it. Goods only bounce back and forth if one warehouse is both an input and an output on opposite ends; the panel can warn about that instead of forbidding it.
- **Not included:** storage, buffer and active-provider roles (as in Factorio's logistic chests). Without a target amount, "storage" has no meaning here, and warehouses already do that job.

### Bit layout (3 memberships of 9 bits)

```
stored = -(2 + x)
x < NetBase (2^22):   1.x value, x = the target's dock ID
x >= NetBase:         network value, packed = x - NetBase
packed bits:  30..28 unused | 27 paused | 26..18 memb 3 | 17..9 memb 2 | 8..0 memb 1
membership (9 bits):  8..7 unused | 6..5 role (0 both, 1 provide, 2 request; 3 read as both) | 4..0 network ID (0 = empty)
```

- **Range split, not a format bit:** 1.x values (`-2 - dockId`) and network values are told apart by where x falls. Dock IDs are in the ten-thousands, far below 2^22, so 1.x saves keep converting on load. The split costs 2^22 of the 2^31 values, not a bit.
- **Overflow guard:** "both" is written as role 0 and role 3 is never written, so slot 3's role bits are never both set and packed stays below 2^31 - 2^23. NetBase + packed then always fits, which is why NetBase may be at most 2^23 - 1.
- **Paused (27):** the ship finishes its job and takes no new one.
- **Unused bits** (30..28, and each membership's 8..7; 9 in all): written 0 and ignored when read, kept free for later use, with 0 meaning today's behaviour. 28 and 8..7 held "depart only when full" and a per-membership priority, both removed (2026-11-07).
- **Format changes:** none planned. A new field takes unused bits with 0 as the old behaviour, so no version marker or migration is needed; a breaking change, if ever unavoidable, would use a small version field rather than another marker bit.
- **Earlier layouts** (bit 30 marker with four 7-bit memberships; bit 29 marker with this layout at x = 2^29 + packed) were only on test saves and are no longer read. A test save holding them decodes to wrong memberships; reset its docks in the network GUI.
- **Access:** all bit work is behind pure helpers in `BPL_FDNet`: `Unpack`, `Pack`, `With`, `WithPaused`.

### Roles and the native flags

The linker lists already say much of what a role says: a dock with output warehouses has demand; a dock with input warehouses has a known supply.

**Decided: providing requires at least one input warehouse.** A dock loads only from its own input warehouses, never from any warehouse it can reach, as it does today. The player sees exactly what a dock will load, and has finer control. A provider membership on a dock without sources does nothing, and the panel says so.

The role is still stored per membership: the lists say what a dock *can* supply or wants, the role says on which network.

### On load

1. Read every freight dock's value and decode it.
2. Convert each old one-to-one pair (A ↔ B) into one fresh network on which both docks have the role "both". This keeps today's behaviour, with one exception: a migrated dock with no input warehouses stops loading, since providing now requires them. The panel (and a toast after migration) should say so.
3. Build, per network, the list of providers and requesters. The working links are the provider × requester pairs.
4. Test migration on its own first: a 1.x save loads, converts, saves and reloads with the same behaviour.

## UI

All in the Loom panel (`WBP_FDPanel`), not injected into the game's dock window. The panel covers every freight dock, member of a network or not: today an unpaired freight dock still shows the game's own supported actions, load-ship bar and departure checklist.

- **Memberships on the panel:** the dock's networks with their roles, for example `1 (provide)`, `3 (both)`, or `none`.
- **Network picker,** opened from there:
  - a row per network, with a role choice per row; at most 3 memberships (the other rows' checkboxes are disabled at 3, saying why);
  - rows for every ID from 1 to the highest in use, plus the next one. Gaps left by demolished or unhooked docks (with 1, 2 and 5 in use: 3, 4 and 6) are still shown, so free numbers are easy to find;

- **Hovering a row:** a minimap of the colony with icons for the selected dock, each provider and each requester on that network.
  - Provide and request icons: icons8's logout-rounded and input (`/Game/Assets/Icons`), red and blue, at 36 px on the divider above the network GUI's Provide and Request headers (the line broken around them); picked over the game's `industry_out` / `industry_in` (2026-11-08).

**Tested (2026-11-04):** copying a paired freight dock and pasting onto an unpaired one changes nothing the mod uses: `activeTradePartnerId`, the input and output lists and the request all stayed as they were. So memberships are not copied natively.

- **Tested (2026-11-08):** the mod sees C, V and Ctrl while a freight dock is selected (`PlayerController.WasInputKeyJustPressed`, keys from `OptionManager.StringToKey`), and Ctrl+V does not set off the game's V hotkeys.

Ctrl+Z undoes that paste while the dock is still shown (one step, no history); the game's Z-layer hotkey fires on it too, and the mod can neither stop nor reverse that. Each shows a toast. Not while the rename popup is open. The linker lists are not copied (read-only to Blueprint).

## Dispatch: global jobs (decided 2026-11-05)

Replaces round-robin (step 5, see "Destinations and dispatch" below), which had each provider decide alone from a guess about the others: it could ship to the same requester twice, sit on a requester another ship already covered, and lose track of cargo across a reload. A central dispatcher hands out **jobs** instead.

### Jobs

- **A job** is one ship's next trip: provider P, requester R, and a **manifest** (per good, how many). Each provider has at most one job (one ship per dock).
- **Single source of truth:** loading, departure, the voyage (target, course home, arrival), the panel and the arcs all read the job. Nothing reads a dock's "current target" any more.
- **Lifetime:** from assignment to delivery. Leaving the network, demolition, or the ship being reassigned cancels it: loading is paused, the dock's per-trip state cleared, and the job's goods already aboard move to the dock's delivered-goods store (as leftovers after a trip). A job already at sea still delivers.
- **Request-only docks** get no jobs. A dock's ship only ever carries goods on networks where the dock provides.
- **Return trips:** ships return home after each delivery; the home dock is the depot. No roaming between docks, no second ship per dock.

### Demand and supply

- **Demand,** per requester R and good: R's output warehouses' unmet requests, minus what is already unloaded at R, minus everything existing jobs carry to R (counted from assignment, so two providers never plan for the same units).
- **Demand age,** per requester and good: how long that demand has been unserved (since it last became positive with no job covering it).
- **Supply,** per idle provider P and good: what P's input warehouses hold free, plus what sits in P's own delivered-goods store that P's own output warehouses don't want (leftovers, below), minus what P's own job already claims.

### Choosing jobs

One pass per dispatcher tick, greedy and global:

1. Score every (idle provider P, requester R) pair sharing a network: **score = Σ over goods (units carried × (1 + age ÷ τ)) ÷ round-trip time**. Units carried, per good, is the smaller of demand and supply, together capped by P's free hold space. Round-trip time comes from the route length and ship speed.
2. Assign the best pair, subtract its manifest from demand and supply, and repeat until no pair scores above zero.

The score is goods delivered per unit of time, weighted by how long the demand has waited: it minimises age-weighted item-seconds of unmet demand. Fresh demand is ranked purely by throughput; old demand gains weight until it wins, so nothing starves. τ (how fast waiting gains weight; first guess 10 game minutes, a demand that has waited τ counts double) is a tuning constant.

### Minimum load (Mod Option)

- **"Minimum load":** None / 25 % / 50 % / 75 % / 90 % (global).
- **When it applies:** at assignment. A job must reach that share of the smaller of P's free hold space and everything R wants that P can supply. A requester wanting only 10 of something can therefore always be served by a job of 10.
- **Waived** once R's demand has waited longer than the "Depart after" time, so a requester with a trickle of demand isn't starved.

### Loading and departure

- **Loading** loads the manifest (the request is still a total to have aboard).
- **Growing manifests:** while loading, the manifest grows when R's demand grows, the hold has room, and P's supply can cover the growth; the growth is claimed at once.
- **Stalls:** once nothing of the job has moved for 20 s (no good gained, none being carried: haulers fetch one good after another), a good whose manifest isn't met is cut from the manifest; its demand returns to the pool. That provider isn't offered the good again until its input warehouses' free stock of it changes (`CutStock`), so a cut good isn't added straight back. Growing a job restarts the good's 20 s clock.
- **Departure:** when the manifest is aboard, the hold is full, the "Depart after" timer runs out (from first freight aboard), or Deliver now.

### Leftovers

Freight that no job delivered (a cancelled voyage, a reload mid-voyage, a requester that no longer wants it on arrival):

- **On arrival home,** goods aboard that no job wants are moved from the hold into the home dock's delivered-goods store (unreserved units only). They show as a pile at the dock and in the panel's "Waiting to unload".
- **As supply:** goods in a dock's delivered-goods store count as that dock's supply where its own output warehouses don't want them. (A dock's own output warehouses get first claim, so a "both" dock's real deliveries are never shipped onward. No separate record of parked goods is kept.)
- **Reuse:** a job that takes them moves the claimed amount from the delivered-goods store straight into the ship's hold (the game loads only what haulers carry aboard, never from the dock's input slot). Only unreserved units are moved.

### Explaining it

The dock GUI shows the job ("Delivering 30 flax, 20 stone to Schoolhouse"), or why the dock is idle: no requester wants what its inputs hold, other ships already cover it, the minimum load isn't reached yet.

### What it settles

From the 2026-11-05 edge-case review: request-only docks shipping (1), leaving a network mid-load (2), the turn not passing (3), stalling on a covered requester (4), double delivery (5), cargo stranded by a reload (6), the course home drifting (7), switch-and-depart in one tick (8), leftovers pinning the destination (9), cargo rerouted mid-load (10), flip-flopping (13). Performance (14): one dispatcher pass per tick can look up each building once and reuse it for the pass.

### Reference: Factorio's LTN mod

LTN (Logistic Train Network) uses the same idea: a network ID as a 32-bit mask. Its answers are worth borrowing:

- **Destination:** demand-driven (FreightDock's job dispatcher, above, is similar). A requester places a request when its stock falls below a per-stop threshold; a central dispatcher pairs it with a provider on a shared network that has enough, and sends one vehicle with exactly that delivery.
- **Depots:** vehicles return to a depot after every delivery, and only idle vehicles are used.
- **Thresholds:** deliveries below a per-stop threshold aren't dispatched, which stops wasteful small trips. FreightDock's nearest equivalents are "Depart after", "Minimum load" and Deliver now.

FreightDock remains its own design (stand-ins, water routes, dock panels); LTN is a reference for dispatch rules, not a template.

### Variables affected

- **Routes:** `RoutePts`, `RouteLen`, `RouteCurves` and `PreviewCourses` become keyed by pair. A pair key can be one int built from the two dock IDs.
- **Voyages:** stay keyed by dock (one ship per dock), plus a destination map.
- **Loading:** `Requested`, `PickupSeen` and `PickupSince` stay per dock, but demand is per destination.

### Risk

- **Rewiring:** most of the pairing and route plumbing changes at once, cutting into the reliability work already done (footprint blocking, course fallbacks, rescan slicing, the stand-in hover route).
- **Silent breakage:** a migration bug could quietly break existing saves' pairs. Migration gets its own test before anything else changes.
- **Rescan cost:** a network with p providers and r requesters needs p × r routes, each with its own A* search. Slicing across frames still applies, but the total work grows.

## Storage library (built)

`Content/Mods/FreightDock/Loom/BPL_FDNet.lm`. The one-to-one checkpoint (step 4) runs on it: each pair is a network of its own, both docks "both". `TargetOf` and `Unpair` call it, `PairAtCursor` and `DrawArcs` are ported to `Loom/BPL_FDPairing.lm`, the panel shows for any paired dock (`IsPaired`), and the panel runs `Migrate` once per load, when the docks are known.

- **Encoding:** `Unpack`, `Pack`, `RoleOn`, `Provides`, `Requests`, `IsMember`, `With` (set or remove one membership; refuses a fourth), `WithPaused`.
- **Queries,** stateless (decoded from every freight dock's value on each call): `FreightDocks`, `Members` (providers and requesters of a network), `InUse` (networks in use, lowest free ID), `RequestersOf` and `ProvidersOf` a dock, in dock ID order for round-robin.
- **Pairing:** `TargetOf` (the single other member, or a 1.x target before migration), `Unpair` (the dock and the other members leave its networks), `Pair` (both leave their networks, then share the lowest free one), `IsPaired`, `Emptied`.
- **Migration:** `Migrate` turns each 1.x pair into the lowest free network with both docks in the role "both"; a 1.x value whose target is gone becomes -1. A converted save can't be read by mod 1.x.
- **Tests:** `Tools/FreightDock/loom_test.py` runs the encoding functions' cases with Loom's test commandlet, against a Python model of the encoding. The queries and `Migrate` need a loaded colony, so they are tested in game.

## Destinations and dispatch (built, step 5; round-robin superseded by global jobs)

- **Routes stay keyed by dock,** to the dock's current destination, and are replanned when it changes (at most once per round trip). Every route function already asks `TargetOf` where to go, so none of them changed. This replaces the "routes per provider-requester pair" plan under Costs; caching one route per pair can come later if replanning ever shows up as slow.
- **Round-robin** (`BPL_FDNet.ChooseDest`, run at the start of each loading plan for a berthed dock): `NetDest` holds each dock's destination, `NetUsed` whether a trip has started since it was chosen. Once idle again after a trip, the turn passes to the next requester (dock ID order) that wants something the dock's input warehouses hold (`Wants`); an idle dock whose destination wants nothing it can load passes it on the same way; with no candidate, the destination stays. A change replans the route and logs "Dock A now delivers to B (i of n)".
- **`TargetOf`** returns the destination (else the first requester; a dock that only requests gets its first provider).
- **Loading plan** (`BPL_FDLoad.Plan`): providing requires input warehouses (none set: nothing is loaded); a requester's need also leaves out what other providers' ships bound for it carry or are loading (`OthersBringing`).
- **Panel:** "Delivering to: Freight Dock N (i of n)", or "Supplied by: ..." for a dock that only requests; a provider without input warehouses says it loads nothing.
- **F5 until the picker:** (removed in step 6) selecting a dock and then another put them on a shared network.
- **Library layering:** Loom refuses Blueprints that use each other, so `BPL_FDNet` is the base (it now holds `DockId` and `SourceStock`); `BPL_FDLoad`, `BPL_FDPairing` and the panel use it, never the other way round.

- **NETWORKS (dock GUI):** the dock's memberships in ascending network order ("1: provide   3: both", or "Not in a network") and an Edit button.
- **Network GUI** (`WBP_FDNetPanel`): Edit opens it to the dock GUI's left, bottoms aligned, in the same frame, background and fonts (the dock GUI passes its brush and fonts: `SetLook`); Edit, now "Close", closes it, as does selecting something else. A table of networks 1 to the highest in use plus one, gaps included, columns Network ID | Provide | Request | Requested goods; each header but the first explains itself on hover. Rows (`WBP_FDNetRow`): the game's tick-box icons (`icons8-tick-box(-unchecked)-96`, tinted gold / muted) as checkboxes for the selected dock (both ticked: "both"), each followed by the network's number of providers / requesters in parentheses, the tooltip naming them; requested goods as icons (`BPL_FDNet.NetRequests`: request levels, `minHold`, whether met or not), dimmed when no provider on the network has the good whitelisted in an input warehouse (`ProvidedGoods`; a warehouse with no whitelist in use, `m_whiteListReceiving` false, counts as providing everything); each good's tooltip (`WBP_FDNetTip`): icon, name, requested and stocked amounts, the requesters asking for it (`AsksForGood`) and the providers able to supply it (`SuppliesGood`). - **Dock names** (`BPL_FDNet.DockName`): the name set in the dock GUI (see Names, step 9); else "Freight Dock <id>". Used in the dock GUI's title and destination line and in the network GUI's provider / requester tooltips; logs keep IDs. (Until 2026-11-07 names came from `[fd]` / `[fn3]` signs.)

## Global dispatch (built, step 7)

- **`Loom/BPL_FDDispatch.lm`,** run every `TickSeconds` of game time from `BPL_FDPairing.Tick` (`Tick` -> `Pass`): `Upkeep` (a returned job `Complete`s: manifest goods still aboard move to the dock's delivered-goods store; a job whose provider and requester no longer share a network, or are gone, is `Cancel`led: `PauseLoading`, `ClearRequested`, loading clocks cleared, manifest goods aboard parked (`Park`)), `Demand` (per "<requester>|<good>": output deficits less goods unloaded there less every undelivered job's manifest; `DemandSince` ages it), `Grow` (jobs still loading), `Assign` (greedy best score; input warehouse stock is pooled per warehouse, so docks sharing one can't both be given the same units; idle reasons are logged when they change; `Give` writes the job, plans the route, logs "Dispatch: dock P -> R: good=n ... (score s)").
- **Job storage** on BP_MapLoad: `JobTo` (provider -> requester), `JobGoods` ("<provider>|<good>" manifest units, "<provider>|<good>|park" units still to move from parked leftovers), `JobState`, `DemandSince`, `IdleWhy` (shown in the dock GUI), `NextDispatch`, `MinLoad`. Not saved: after a reload there are no jobs, goods aboard count as supply, and demand ages restart.
- **Job states** (`JobState`, per provider dock; `BPL_FDNet.SetState` is the only writer and logs each move as "State: dock <id> <from> -> <to>", marking one `StateMove` doesn't have): idle (no entry) -> loading (`Give`) -> depart pending (ready or sent with Deliver now, goods still being carried) -> outbound (`Depart`) -> dwell (delivered, at the requester) -> homeward -> returned (home; `DockTick` leaves it alone, the dock GUI shows "Returned") -> idle (`Complete`, next pass). Loading and depart pending go to idle on `Cancel`; outbound and dwell go straight to returned for a timed trip or a ship that left its berth. `Voyages` and the voyage maps hold a stand-in's data only; a timed trip has a state without them. `BPL_FDNet.IsSailing` is outbound, dwell or homeward.
- **Generated graphs left for voyages:** `VoyageTick` (the timer's function), `SpawnStandIn` and `SpawnFling` (Loom can't spawn actors). `StartVoyage` is `BPL_FDVoyage.StartVoyage` and `DrawRoute` is `BPL_FDPairing.DrawRoute`.
- **Jobs live in BP_MapLoad, not a dispatcher object:** `BPL_FDNet.TargetOf` must read them, and a dispatcher object using `BPL_FDNet` would make a cycle, which Loom refuses.
- **Supply** (`Supply`): free stock in the input warehouses, everything aboard, and unreserved goods in the dock's delivered-goods store that its own outputs don't want.
- **Trip time** is estimated: 2 x straight-line distance / `ShipSpeed` + `Overhead()` (60 s). The real route is planned only when a job is given.
- **`TargetOf`** returns the job's requester (`BPL_FDNet.DockIn`, a lookup over `MapLoad.Docks`), else none: a dock without a job is skipped by `FreightTick`, so no fdgen graph changed.
- **Loading plan** (`BPL_FDLoad.Plan`): loads the manifest (got = in the hold + being carried; request = the manifest, or the hold when more; goods outside the manifest leave the request); `RequestFor` (Loom) writes it with each input slot's capacity = request less the hold; `Remaining` = manifest not yet got; a good not picked up for 20 s is cut to what is got; parked leftovers the job takes board directly (`BoardParked`). A ship holds only its job's freight: anything else aboard (beyond the manifest, provisions aside) is parked each plan (`BPL_FDNet.ParkStray`), and at completion or cancel everything but provisions is.
- **Shrinking** (`BPL_FDDispatch.Shrink`, each pass after upkeep): a loading job keeps at most what its requester still wants of each good (its unmet requests less what is unloaded there, shared first with jobs under way). The rest leaves the manifest and what of it is aboard is parked; a job left empty is cancelled.
- **"Minimum load" Mod Option** (`BPL_FDOptions`, `freightdock.minLoad`): None / 25 / 50 / 75 / 90 %; `BPL_FDDispatch.MeetsMinimum`.
- **Dock GUI:** "Delivering to: <name>" with the manifest as icons, "Supplied by: ..." for a dock that only requests, "Idle: <reason>" for a provider without a job.
- **Removed:** round-robin (`ChooseDest`, `Wants`, `Turn`, `OthersBringing`, `NetDest`, `NetUsed`) and the 60 s pause (`StallLeft`, `Retry`).
- **Tests:** `loom_test.py` adds `BPL_FDDispatch` cases (`GoodValue`, `MeetsMinimum`, `GoodOf`) and `JobKey` / `ParkKey`.

## Explaining and controlling (built, step 9)

Everything is shown per dock, in its dock GUI; there is no colony-wide display. The only toasts are copy, paste and undo's (Ctrl+C / V / Z).

- **Storage:** 3 memberships of 9 bits and a paused flag (see Bit layout).
- **INCOMING** (dock GUI, for a dock that requests): per good its output warehouses want, how much is still wanted (less what is unloaded there), how much is on its way, and from where (loading at the provider, or sailing with the arrival time), or why nothing comes. The dispatcher records the reason per "<target>|<good>" left open after each pass (`BPL_FDDispatch.Explain`, `MapLoad.WhyNot`): no provider on its networks, no provider stock, providers off duty, providers missing ships (the only providers with the good have no ship: none at home and none on a job), below minimum load (n of m), or providers busy.
- **Pause** (beside the SHIP heading): the ship finishes its job and takes no new one ("Idle: paused").
- **Deliver now** sits beside it, disabled with the reason as its tooltip when it can't act (ship away, nothing aboard, already pressed); it no longer toasts. It is enabled as soon as anything is aboard, also while the ship waits for final cargo, and the ship leaves in the same frame (`FreightTick` runs at once).
- **Waiting for final cargo** (everything picked up, haulers still on the way) has no time limit; Deliver now ends it. The depart-after countdown ("Waiting for cargo - leaving automatically in x:xx") shows in the last third of the depart-after time.
- **Short departures:** a ship that leaves with less than its manifest has the manifest cut to what is aboard (`BPL_FDDispatch.Trim`), so the rest is open demand for other providers; the dock GUI notes "Left at time limit: 39 of 50 Flax" or, after Deliver now, "Sent early: ..." until the job ends (`MapLoad.JobShort`).
- **Routes** are planned a little each frame (`BPL_FDVoyage.RouteStep`, 1 ms a frame: A* with a binary heap, then the path pulled straight); the selected dock shows no route line until its route is ready. A ship about to sail finishes its route at once (`PlanNow`). A ship that departs before a rescan has caught up with a new building sails its planned course.
- **Dropped goods:** a good cut from the job as stalled is listed under the ship's state ("Dropped: 3 Flax (no hauler)") until the job ends (`MapLoad.JobDropped`). A good cut to nothing leaves the job; a loading job left with nothing is cancelled, freeing the dock.
- **Names:** a click on the dock GUI's title renames the dock, and a click on a network's ID in the network GUI renames the network ("3 Food" in both GUIs), in a popup centred over what was clicked (`WBP_FDRename`). Its text box is the game's own (`DebugRow_TextEntry`, as the ship rename uses), so typing doesn't fire the game's hotkeys; Enter or a click elsewhere keeps the text, Escape cancels, an empty name restores the default. Kept in the colony's event flags (`Loom/BPL_FDStore.lm`: `fd.d<dockId>=…`, `fd.n<id>=…`, capitals escaped; see Extra storage), so they travel with the save. Names are cut at 60 characters. Names of demolished docks are removed on load (see Jobs across a reload).
- **Version:** on each load the colony records the FreightDock version that last ran on it (`fd.ver`, `BPL_FDStore.Version()`, kept equal to the `.uplugin`'s `Version`); colonies from before 2026-11 have none. The load line in the modlog says which version the colony's data came from.
- **Minimum load with "Depart after: Never":** the waiting exemption applies after 10 minutes.
- **Ping-pong:** a provider doesn't ship goods its own output warehouses still request.
- **Crews off duty** (`BPL_FDNet.OnDuty`: at night, and in the morning until the dock's first worker is at work, `MapLoad.CrewArrived`; docks have no overtime): an off-duty provider is offered only what needs no haulers (aboard, or parked leftovers), so such a job can still sail at night; a job loading when the crew leaves keeps its goods, its stall and depart-after clocks wait ("Crew off duty"), and it doesn't grow. INCOMING says "Providers off duty" when only off-duty providers hold the good.

## Jobs across a reload (built 2026-11-09)

- **One clock:** every persistent FreightDock time (loading since, departing since, departed at, the dwell's end, demand ages, stall clocks) is on the colony clock, `WorldTime.m_totalWorldTimeElapsed` (`BPL_FDNet.ColonyTime`): it stops when paused, runs with game speed and is kept in the save (confirmed in game). Scheduling and cosmetic times stay on game time.
- **Ported:** `FreightTick` and `VoyageArrive` are in Loom (`BPL_FDLoad.FreightTick`, `BPL_FDVoyage.VoyageArrive`); fdgen keeps a thin `FreightTick` (its timer) and `SpawnFling` (Loom can't spawn actors). Deliver now marks `ManualDepart` instead of a negative time.
- **Entries** in the colony's event flags (`BPL_FDNet.JobEntry`, `SaveJobs`): `fd.j<provider>` per job - format version, requester, the state, the clocks, the Deliver now flag, the dwell end, the manifest `good:units:parked`, the short-departure and dropped-goods notes (lower case, `/` stored as `-`) - and `fd.a<requester>` with its demand ages. Written where they differ from what is stored, after each dispatch pass and `FreightTick` and when a voyage arrives (at the requester or home) or turns for home; `DropJob` removes a job's entry. Job entries may be up to 900 characters (`BPL_FDStore.SetLong`).
- **Restore** (`BPL_FDLoad.RestoreJobs`, once per load when the buildings are indexed and the load's rescan is done; until then the dispatcher, `FreightTick` and `SaveJobs` wait, `JobsRestored`): each job comes back in its saved state (format 1 entries, from before the states, have it worked out from their clocks and phase); a job at its dock is as it was, a returned one is closed by the next pass; a sailing job sails on - `BPL_FDVoyage.StartVoyage` again, the stand-in placed by the colony clock (outbound by the time since departure while the manifest is still aboard, at the requester until the dwell ends, homeward by the time since) and facing its course (`PlaceStandIn`). A job whose provider, ship or requester is gone is dropped. `FreightTick` runs at once: a save brings the docks' input slots back without capacity, and the game would turn away haulers already carrying goods.
- **Cleanup:** entries of dropped jobs, demand ages no longer open and names of docks whose building is gone are removed; network names stay; keys of other kinds are left alone.
- Not kept: stall clocks restart, and the bar on a good cut after a stall is lost.
