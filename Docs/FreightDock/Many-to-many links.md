# Many-to-many dock links (tabled)

Status: designed in outline, not implemented. A persistence spike succeeded (2026-11-01); its code is on branch `freightdock-packed-links-spike`. The released mod (1.1) still links freight docks strictly one-to-one.

## Goal

Let freight docks take part in **networks** instead of fixed pairs. Every provider on a network can supply every requester on it, so goods can fan out, fan in and chain across islands.

## Current design (one-to-one)

- **Pairing storage:** the game's own `WorkDock.activeTradePartnerId` (int32), as `-2 - partnerDockId`.
  - Paired means a value of -2 or below; `-1` is the game's own "no partner".
  - The game never sets values of -2 or below, so its own trade logic ignores them.
- **Persistence:** the field survives the game's `.whisker` save format even though it has no `CPF_SaveGame` flag. The mod adds no save data of its own; all other state is rebuilt on load.
- **Native flags:** each dock's `StockpileLinker` holds two lists the game saves itself: "Deliver to" (`m_destStockpileIds`) and "Pick up from" (`m_sourceStockpileIds`). The mod already reads both: the partner's "Deliver to" warehouses make the demand (`DeficitsFor`), and this dock's "Pick up from" warehouses cap what is loaded (`BPL_FDLoad.Plan`).
- **Per-dock state:** runtime state in BP_MapLoad is keyed by dock ID and assumes one partner per dock:
  - routes: `RoutePts`, `RouteLen`, `RouteCurves`, `PreviewCourses`;
  - voyages: `Voyages`, `VoyageShip`, `VoyageSpline`, `VoyageDist`, `VoyagePhase`, `VoyageWait`, `VoyageBerth`, `VoyagePartner`, `VoyageEndFwd`;
  - loading: `LoadingSince`, `DepartingSince`, `DepartedAt`, `Requested`, `PickupSeen`, `PickupSince`;
  - the partner itself comes from `PartnerOf`.
- **Code:** graph functions are generated by fdgen (`Tools/FreightDock`); the panel (`UI/WBP_FDPanel.lm` and its rows), the loading plan (`Loom/BPL_FDLoad.lm`) and the unloading animation (`Loom/BP_FDFling.lm`) are written in Loom.

## Persistence spike: result

Question: can one int32 hold several links and still survive a save/load?

- **Test value:** `-(2 + (5 | 7<<6 | 9<<12 | 33<<18 | 62<<24))` = **-1048875463**.
- **Procedure:** `SpikeStorage` (run once, about 2 s after load) wrote the value into an unpaired freight dock (11700); the game was saved and reloaded.
- **Result:** the reloaded dock read back -1048875463 exactly. The existing pair (11769 ↔ 11691) was untouched, route planning ran normally, and nothing in the game reacted to the odd value.
- **Conclusion:** at least 30 bits of payload survive a save, with no extra save data.

Spike leftovers:

- **Code:** `SpikeStorage`, `SpikeTick` and the variable `SpikeFrames`, on the spike branch only (`Tools/FreightDock/fdgen/features/spike.py`); they were left out of the merge. Removal steps are in that file's docstring.
- **Test dock:** the test save's dock 11700 still holds the test value; the current mod sees it as paired with a dock that doesn't exist. To clear it, press F5 on that dock, then F5 with no dock selected.

Other places were tested on 2026-11-04 (see Extra storage): only the profile save's key-value store also survives, and it isn't part of the colony save. 30 bits are enough for the layout below.

## Decided: network membership

A dock stores **which networks it belongs to, and in which role**, never which docks it links to. There is no per-map dock limit and no per-dock link limit. (The earlier slot format, 63 docks with about 4 links each, is dropped; its limits were a large part of why the work was tabled.)

- **Networks:** IDs 1–31.
- **Memberships:** up to 4 per dock, each with its own role: provide, request, or both.
- **Links:** on each network, every provider supplies every requester; a dock never supplies itself.
- **Example:** dock A provides on 1; dock B requests on 1 and provides on 3; dock C requests on 3. The result is a chain, A → B → C.
- **Roles per membership** matter for chains like this one: a single role per dock could not express B.
- **Provide and request on the same network** is allowed. It is today's two-way pairing, and migration relies on it. Goods only bounce back and forth if one warehouse is both a "Pick up from" and a "Deliver to" on opposite ends; the panel can warn about that instead of forbidding it.
- **Not included:** storage, buffer and active-provider roles (as in Factorio's logistic chests). Without a target amount, "storage" has no meaning here, and warehouses already do that job.

### Bit layout (4 memberships of 7 bits)

```
stored = -(2 + packed)
packed bits:  30     | 29       | 28           | 27..21 | 20..14 | 13..7  | 6..0
              format | reserved | depart full  | memb 4 | memb 3 | memb 2 | memb 1
membership (7 bits):  6..5 role (0 unused, 1 provide, 2 request, 3 both) | 4..0 network ID (0 = empty)
```

- **Format bit (30):** marks the new format. Old values (`-2 - dockId`, dock IDs far below 2^30) lack it and are converted on load.
- **Reserved bit (29):** kept clear. With bits 30 and 29 both set, `packed` could reach 2^31 - 1 and `-(2 + packed)` would overflow int32.
- **Depart only when full (28):** a per-dock version of the global "Depart after: Never".
- **Access:** keep all bit work behind two pure helpers, `Unpack(Int) -> memberships, flags, IsNew` and `Pack(...) -> Int`. Loom has `&`, `|`, `/` and `%` on ints, so this is straightforward.

### Roles and the native flags

The linker lists already say much of what a role says: a dock with "Deliver to" warehouses has demand; a dock with "Pick up from" warehouses has a known supply.

**Decided: providing requires at least one "Pick up from" warehouse.** A dock loads only from its own "Pick up from" warehouses, never from any warehouse it can reach, as it does today. The player sees exactly what a dock will load, and has finer control. A provider membership on a dock without sources does nothing, and the panel says so.

The role is still stored per membership: the lists say what a dock *can* supply or wants, the role says on which network.

### On load

1. Read every freight dock's value and decode it.
2. Convert each old one-to-one pair (A ↔ B) into one fresh network on which both docks have the role "both". This keeps today's behaviour, with one exception: a migrated dock with no "Pick up from" warehouses stops loading, since providing now requires them. The panel (and a toast after migration) should say so.
3. Build, per network, the list of providers and requesters. The working links are the provider × requester pairs.
4. Test migration on its own first: a 1.x save loads, converts, saves and reloads with the same behaviour.

## UI

All in the Loom panel (`WBP_FDPanel`), not injected into the game's dock window. The panel covers every freight dock, member of a network or not: today an unpaired freight dock still shows the game's own supported actions, load-ship bar and departure checklist.

- **Memberships on the panel:** the dock's networks with their roles, for example `1 (provide)`, `3 (both)`, or `none`.
- **Network picker,** opened from there:
  - a row per network, with a role choice per row; at most 4 memberships, so one must be removed before a fifth is added;
  - rows for every ID from 1 to the highest in use, plus the next one. Gaps left by demolished or unhooked docks (with 1, 2 and 5 in use: 3, 4 and 6) are still shown, so free numbers are easy to find;
  - beside each row: the number of providers and requesters, and the icons of the resources that have requests set on that network (from its requesters' "Deliver to" warehouses), whether or not they are met and regardless of amount;
  - the tooltip of a row: demand and satisfaction per resource.
- **Naming:** networks have no names while only their IDs are stored (a signpost could hold names; see Extra storage). Show numbers 1–31.
- **Colours:** a fixed palette, one colour per network ID, for the minimap and arcs. 31 colours that stay distinct at a glance are hard to find, so the number is always shown next to the colour; the palette only has to help, not identify on its own. Choosing it is still to do.
- **Hovering a row:** a minimap of the colony with icons for the selected dock, each provider and each requester on that network.
  - Provide and request icons: the game probably has them (the dock window's linkage assigner shows similar ones). Not yet checked.
  - The network's links could also be drawn as arcs in the world, as `DrawArcs` does for pairs today.
- **F5 pairing: removed.** Memberships are set only in the panel. The pairing key option (`freightdock.pairKey`) and its code go with it.

### Copy and paste of building settings

The game copies and pastes a building's settings with Ctrl+C / Ctrl+V. Some building windows also have a `CopyPasteWidget` (buttons `btn_copy`, `btn_paste`; `Context` is the building), but the dock window has none.

**Tested (2026-11-04):** copying a paired freight dock and pasting onto an unpaired one changes nothing the mod uses: `activeTradePartnerId`, the "Pick up from" and "Deliver to" lists and the request all stayed as they were. So memberships are not copied natively.

- **Copying memberships ourselves** would need the mod to notice Ctrl+C / Ctrl+V on a freight dock: read the keys while a freight dock is selected (as the pairing key is read today), remember the dock on copy, and apply its memberships (and, if wanted, its linker lists cannot be written: they are read-only to Blueprint) on paste. Not yet tried; whether the game consumes the keys before the mod sees them is unknown.
- **Alternative:** a "copy from" picker in the panel instead of the keyboard.

### Extra storage

Candidates tested on 2026-11-04 with a temporary probe (written, then saved, reloaded and the game restarted):

| Candidate | Result |
|---|---|
| **Signpost text** (`signPost` → `Signpost.shownMessage`) | Readable, but **not writable**: the field is read-only to Blueprint, and the game sets it through a sim action (`SIGNPOST_SET_MSG`) that mods can't send. Hiding the sign's text panel (`Widget.SetVisibility`) works but doesn't survive a reload. So a sign can only hold text the player types. |
| **Linker lists** (`m_sourceStockpileIds`, `m_destStockpileIds`) | Read-only to Blueprint. |
| **A made-up key in the dock's request** (`m_requiredEmbarkSupplies_dockSpecific`) | Lost on save. While present it showed in the game's departure checklist ("crew 0/12345"). |
| **A made-up slot in the dock's goods-from-sea store** | Lost on save. While present it showed in the Logistics tab ("Text block 0/54321"). |
| **Profile save key-value store** (`Backbone.GetSave()` → `SetString` / `SetNumber`, then `Save`) | **Survives** reloads and a game restart. |

The profile store (`GenericSaveGame`, slot `Profile_0`) belongs to the player, not the colony: data has to be keyed by the colony's save name (`ArcoSystems.m_associatedSave`, e.g. `Ogdenville - test 3`). It doesn't travel with a save file, and "save as" under a new name or a renamed save loses the link.

- **Fit for:** extras that can be lost without harm, such as network names and per-network colours.
- **Not fit for:** anything essential. Memberships and roles stay in `activeTradePartnerId`.

The 30-bit design needs none of this. The profile store is the way to add network names later.

### Minimap

Whiskerwood has no minimap widget of its own. Loom's minimap demo (https://loom.pierrekin.me/demos/minimap/) shows how to build one:

- a render target (`KismetRenderingLibrary.CreateRenderTarget2D`) shown in an `Image` (`SetBrushResourceObject`);
- terrain read from `ArcoSystems.m_terrain`: water depth from `Cells2D[..].WaterDepth`; land height from the top cell with the solid flag in `TypesAndFlags`;
- each cell drawn as two triangles with `BeginDrawCanvasToRenderTarget` / `K2_DrawTriangle` / `EndDrawCanvasToRenderTarget`, a few rows per frame (the demo: 128 × 128 cells, 2 rows a tick, about 64 ticks per full pass), ticking while paused.

For FreightDock:

- **One map per loaded save:** built after load, a few rows a frame; not saved.
- **Terrain only:** buildings aren't drawn into the map, so building and demolishing need no redraw. Docks and warehouses are icon widgets over the image, placed from their world positions.
- **Refresh:** a fresh pass every 10 minutes or so, for terraforming.

## Dispatch (the hardest part)

**Decided: round-robin.** A provider's ship serves its requesters in turn, skipping a requester that wants nothing the provider's "Pick up from" warehouses hold. It is the simplest rule to build and for players to follow.

- **Loading:** the provider loads for the requester whose turn it is; the ship sails there, returns, and the turn passes on.
- **Assignment:** several providers can still serve one requester, so each provider's plan must subtract every ship already bound for that requester (aboard, waiting there, being carried), or two providers fill the same deficit. Today one partner makes this simple.
- **Explaining it:** the panel must show which requester the ship is loading for, and why one is skipped (nothing it wants at the sources, another provider already covering it, paused after a stall). This is as much work as the rule itself, and simpler with round-robin than with a demand-based rule.
- **Return trips:** ships return home after each delivery, as now. The home dock acts as the depot.
- **Not planned:** ships roaming between docks (C → A → B), and more than one ship per dock. The game ties one ship to one dock, and the stand-ins rely on that; the answer to "more ships" is another dock beside the first.

### Reference: Factorio's LTN mod

LTN (Logistic Train Network) uses the same idea: a network ID as a 32-bit mask. Its answers are worth borrowing:

- **Destination:** demand-driven (FreightDock chose round-robin instead, above). A requester places a request when its stock falls below a per-stop threshold; a central dispatcher pairs it with a provider on a shared network that has enough, and sends one vehicle with exactly that delivery.
- **Depots:** vehicles return to a depot after every delivery, and only idle vehicles are used.
- **Thresholds:** deliveries below a per-stop threshold aren't dispatched, which stops wasteful small trips. FreightDock's nearest equivalents are "Depart after", Deliver now, and the per-dock "depart only when full" bit.

FreightDock remains its own design (stand-ins, water routes, dock panels); LTN is a reference for dispatch rules, not a template.

## Costs

Rough scope: about 30 of the generated BP_MapLoad functions change. **Each fdgen function that needs changing is replaced by Loom code**, not edited in fdgen, so the work moves the mod steadily into Loom.

| Area | Functions now (fdgen) | Change |
|---|---|---|
| Storage | `PartnerOf`, `Unpair`, `LogLinks` | Membership pack/unpack, network index and link queries (new Loom library) |
| Load | `RefreshDocks`, or a new load step | Decode, migrate old pairs, build the network index |
| Pairing input | `PairAtCursor`, `ReadPairKey`, `PairKeyTick`, `RegisterOptions` (pairing key option) | Removed; memberships are edited in the panel. `PairKeyTick` also runs `StandInClick` and `PanelTick`, which move to a new tick |
| Routes | `PlanRoute`, `FindPath`, `RouteCurve`, `DropRouteCurve`, `MakeCourse`, `BuildRouteLine`, `ShowRouteLine`, `DrawRoute`, `PreviewCourse`, `RouteStillClear`, `ScanRouteStep` | Key routes by provider–requester pair instead of source dock. Rescans replan every pair touching changed cells |
| Voyages | `FreightTick`, `StartVoyage`, `VoyageTick`, `VoyageArrive`, `WaitHeading`, `StandInClick` | Choose a destination per departure; voyage state records it |
| Loading | `UpdateRequest` (already calls `BPL_FDLoad.Plan`), `DeficitsFor`, `TransferFrom`, `DeliverSelected`, `IsFreightDock` | Demand of the requester whose turn it is; subtract every ship bound for it; load only from "Pick up from" warehouses; "paired" becomes "has a membership" |
| Arcs | `DrawArcs`, `PairArcs` | Draw the selected dock's networks in their colours |
| Panel | `WBP_FDPanel` (Loom) | Memberships, picker, minimap, dispatch explanations, copy/paste hook |

### Variables affected

- **Routes:** `RoutePts`, `RouteLen`, `RouteCurves` and `PreviewCourses` become keyed by pair. A pair key can be one int built from the two dock IDs.
- **Voyages:** stay keyed by dock (one ship per dock), plus a destination map.
- **Loading:** `Requested`, `PickupSeen` and `PickupSince` stay per dock, but demand is per destination.

### Risk

- **Rewiring:** most of the pairing and route plumbing changes at once, cutting into the reliability work already done (footprint blocking, course fallbacks, rescan slicing, the stand-in hover route).
- **Silent breakage:** a migration bug could quietly break existing saves' pairs. Migration gets its own test before anything else changes.
- **Rescan cost:** a network with p providers and r requesters needs p × r routes, each with its own A* search. Slicing across frames still applies, but the total work grows.

## Decisions

Decided:

1. **Dispatch:** round-robin among the requesters that want something the provider's sources hold.
2. **Providing** requires at least one "Pick up from" warehouse.
3. **F5 pairing** is removed.
4. **Colours:** a fixed palette, one per network ID, always shown with the number.
5. **Minimap:** terrain only, refreshed about every 10 minutes.

Found out (2026-11-04):

1. The game's paste doesn't copy anything the mod uses (see Copy and paste).
2. Signposts can't be written by the mod; only the profile save's key-value store also survives, outside the colony save (see Extra storage).
