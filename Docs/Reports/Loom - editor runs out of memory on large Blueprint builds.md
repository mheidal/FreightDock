# Editor runs out of memory rebuilding large Blueprints: a "Blueprint modified" notification per link

## Summary

Rebuilding a large Blueprint in the editor (LoomEditor, in-editor build on save) briefly allocates many gigabytes:
7 GB for one of our widget Blueprints, 41 GB for another, 44 GB for the minimal example below. The memory is freed on
the next editor tick, but the allocator keeps it committed, so the editor's commit grows over a session until Windows
refuses an allocation:

```
Ran out of memory allocating 4191714 (4.0 MiB) bytes with alignment 2.
Last error msg: The paging file is too small for this operation to complete.
... UnrealEditor-LoomEditor.dll!FLoomBuild::Run() [LoomBuild.cpp:308]
```

Each link Loom makes (`FLoomApplier::OpLink`) marks the Blueprint modified, twice over, and so does each pin default
(`OpDefault`). Every mark has the Content Browser copy the Blueprint's asset data, including its whole
Find-in-Blueprints search index, into an update held until the next tick. Memory is (links + defaults) × index size;
both grow with the Blueprint, so the spike grows with roughly the square of the Blueprint's size. The same marks make
builds slow (each also walks every node of the Blueprint).

## Environment

- LoomEditor 0.1.0 (in-editor build), Unreal Engine 5.8 editor (a game's modding engine build), Windows 11.
- 31 GB RAM, 32 GB system-managed page file (62.5 GB commit limit, ~37 GB used by other programs); Mimalloc.

## Minimal example

`loom_link_repro.py` (attached) writes a function library with one function: `let x = A`, then `x += 1` repeated N
times, then `return x`. Each line is a local get, an `Add_IntInt` call and a local set: about three links and one pin
default.

```
python loom_link_repro.py <project>/Content/LoomRepro/BPL_LoomLinkRepro.lm 1500
```

Build it in the editor, then change N and save, twice (the first rebuild after an editor start doesn't spike for us;
later ones do). Watch `UContentBrowserAssetDataSource` with `-llm -llmcsv` (`Saved/Profiling/LLM/LLM_*.csv`) or
`stat LLMFULL`. With N = 1500, unpatched: 44 GB peak, a 45 s build. N = 500 shows it at about a ninth of that.

## The chain (UE 5.8 source)

Per link (`OpLink` → `UEdGraphSchema_K2::TryCreateConnection`):

1. `EdGraphSchema_K2.cpp:2294` `UEdGraphSchema_K2::TryCreateConnection`: the base connection, then
   `FBlueprintEditorUtils::MarkBlueprintAsModified(Blueprint)`.
2. Inside the base connection, `PinConnectionListChanged` on both nodes. `K2Node.cpp:515`
   `UK2Node::PinConnectionListChanged` resets a linked input pin's default with
   `Schema->ResetPinToAutogeneratedDefaultValue(Pin)`, whose `bCallModifyCallbacks` defaults to true: another
   `MarkBlueprintAsModified`.

Per pin default (`OpDefault` → `UEdGraphSchema_K2::TrySetDefaultValue` / `TrySetDefaultObject`, `bMarkAsModified`
defaulting to true): another `MarkBlueprintAsModified`.

Each mark:

3. `BlueprintEditorUtils.cpp:1922` `MarkBlueprintAsModified`: clears cached data on every K2 node of the Blueprint,
   then `Blueprint->PostEditChangeProperty(...)` (line 1966) → `OnObjectPropertyChanged`.
4. `ContentBrowserAssetDataSource.cpp:3534` `UContentBrowserAssetDataSource::OnObjectPropertyChanged`:
   `FAssetData AssetData(InObject)`, then `QueueItemDataUpdate(...MakeItemModifiedUpdate(CreateAssetFileItem(AssetData)))`.
5. `Blueprint.cpp:1112-1122` `UBlueprint::GetAssetRegistryTags` (called by that `FAssetData` constructor) adds the
   Blueprint's Find-in-Blueprints index as the `FiBData` tag: one JSON entry per graph, node and pin (titles, pin names,
   types, defaults, comments), 0.74 M characters for our 7 GB Blueprint, 1.7 M for the 41 GB one. Each queued update
   holds a full copy until the next tick.

Not the cause: Loom's `SkipGarbageCollection` (`obj gc` freed 0.4 GB), leaked objects (UObject totals flat), GPU memory.

| Blueprint | Unpatched | Patched |

| Widget Blueprint, FiB 0.74 M chars | 7,239 MB, ~10 s | 630 MB, ~6 s |
| Widget Blueprint, FiB 1.7 M chars (4,581 links, 637 defaults) | 41,190 MB, ~45 s | 2,885 MB, ~12 s |

Notifications on the Blueprint per op in one build of the minimal example: unpatched, links 4,507 (with only the K2
schema's mark avoided); patched, 0. Linking time 10 s → 0.17 s.

## Fix (applied locally, measured above)

```cpp
// LoomApplier.cpp
static TAutoConsoleVariable<bool> CVarLoomDeferLinkMarks(
	TEXT("Loom.DeferLinkMarks"), true,
	TEXT("Mark a Blueprint modified once after its links and pin defaults rather than after each ..."));

// FLoomApplier::OpLink, in place of Schema->TryCreateConnection(From, To)
	const bool bDefer = CVarLoomDeferLinkMarks.GetValueOnGameThread();
	bool bLinked = false;
	if (bDefer)
	{
		// MarkBlueprintAsModified does nothing while the Blueprint is being compiled: this keeps the node's
		// default reset (UK2Node::PinConnectionListChanged) from marking it.
		const bool bWasBeingCompiled = Blueprint->bBeingCompiled;
		Blueprint->bBeingCompiled = true;
		bLinked = Schema->UEdGraphSchema::TryCreateConnection(From, To);  // base: no per-link mark
		Blueprint->bBeingCompiled = bWasBeingCompiled;
	}
	else
	{
		bLinked = Schema->TryCreateConnection(From, To);
	}
	...
	bLinksUnmarked |= bDefer;

// FLoomApplier::OpDefault
	GetDefault<UEdGraphSchema_K2>()->TrySetDefaultObject(*Pin, Loaded, !bDefer);   // and TrySetDefaultValue
	bLinksUnmarked |= bDefer;

// FLoomApplier::OpCompile, first thing
	if (bLinksUnmarked)
	{
		FBlueprintEditorUtils::MarkBlueprintAsModified(Blueprint);
		bLinksUnmarked = false;
	}

// LoomApplier.h, FLoomApplier
	bool bLinksUnmarked = false;
```

`OpLink` only accepts `CONNECT_RESPONSE_MAKE`, so the base schema's connection does what the K2 one would, less the
mark; the nodes still get `PinConnectionListChanged`. The console variable is only there to compare (0 restores the
old behaviour).

## Remaining

With the fix, our largest Blueprint still peaks at ~2.9 GB: about 740 notifications from structural changes in one
build (variables 220 for 69 ops, functions 436 for 60 ops, widgets 41, nodes 36), through
`MarkBlueprintAsStructurallyModified` → skeleton compile → `MarkBlueprintAsModified`. Those regenerate the skeleton
class later ops depend on, so they can't simply be suppressed; batching them (e.g. adding all variables, then one
structural mark) would remove most of the rest.

## Related, smaller

- `OpCompile` compiles with `EBlueprintCompileOptions::SkipGarbageCollection` and nothing collects afterwards; the
  editor doesn't collect on its own while idle, so each rebuild's replaced classes and objects stay until something
  else triggers a collection.
- A handled ensure during builds of a widget Blueprint that uses a class from the game's cooked content:
  `Malformed Blueprint class (RoundedFrameWithHeaderIcon_C) - bad node dependency ... K2Node_VariableGet ...
  Currently compiling: WBP_FDPanel` (`BlueprintEditorUtils.cpp:828`, from `FLoomApplier::OpCompile`). The cooked
  class has no `ClassGeneratedBy`; the build completes. Probably the engine's check, not Loom.
