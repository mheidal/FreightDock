# Content Browser: a full FAssetData (with FiBData) queued per OnObjectPropertyChanged, multi-GB spikes

## Summary

`UContentBrowserAssetDataSource::OnObjectPropertyChanged` builds a new `FAssetData` from the live object and queues
an item-modified update for every notification, with no coalescing per object. For a Blueprint, the `FAssetData`
constructor calls `UBlueprint::GetAssetRegistryTags`, which adds the whole Find-in-Blueprints search text
(`FiBData`). When a tool changes a Blueprint in many small steps in one frame (here, one notification per pin link
via `UEdGraphSchema_K2::TryCreateConnection` → `MarkBlueprintAsModified`), the queue holds one full copy of that text
per step until the next tick.

Measured with `-llm -llmcsv` on UE 5.8 (editor): the `UContentBrowserAssetDataSource` LLM tag peaked at 7.2 GB for a
widget Blueprint with 0.74 M characters of FiB data, and at 41 GB for one with 1.7 M, falling to ~0 MB on the next
sample. With Mimalloc the freed memory stays committed (`FMallocUnused` ~9.5 GB after one spike), so repeated edits
end in "Ran out of memory ... The paging file is too small". Happens with no Content Browser tab open.

## Path (UE 5.8 source)

1. `EdGraphSchema_K2.cpp:2294` `UEdGraphSchema_K2::TryCreateConnection` → `FBlueprintEditorUtils::MarkBlueprintAsModified`
   after each connection; and within the connection, `K2Node.cpp:515` `UK2Node::PinConnectionListChanged` →
   `ResetPinToAutogeneratedDefaultValue(Pin)` (modify callbacks on) → another `MarkBlueprintAsModified` per linked
   input pin. `TrySetDefaultValue` / `TrySetDefaultObject` do the same per pin default.
2. `BlueprintEditorUtils.cpp:1966` `MarkBlueprintAsModified` → `Blueprint->PostEditChangeProperty` →
   `FCoreUObjectDelegates::OnObjectPropertyChanged`.
3. `ContentBrowserAssetDataSource.cpp:3534` `OnObjectPropertyChanged` → `FAssetData AssetData(InObject)` →
   `QueueItemDataUpdate(FContentBrowserItemDataUpdate::MakeItemModifiedUpdate(CreateAssetFileItem(AssetData)))`.
   `OnObjectPreSave` (line 3546) does the same.
4. `Blueprint.cpp:1112-1122` `UBlueprint::GetAssetRegistryTags` → `FiBData` tag with the full search text.

Memory is notifications × FiB size; both grow with the Blueprint, so the spike grows with roughly its square
(2.3× the FiB data gave 5.7× the spike).

## Reproduction

Any tool or script that links a few thousand pins in one Blueprint through `UEdGraphSchema_K2::TryCreateConnection`
in one frame (we hit it with a Blueprint text-compiler plugin rebuilding a large widget Blueprint). Watch the
`UContentBrowserAssetDataSource` tag in `stat LLMFULL` or `-llmcsv`, and `FMallocUnused`.

## Suggestions

- Coalesce item-modified updates per object within a tick, building the `FAssetData` once when the queue is
  processed rather than per notification.
- Or skip the Content Browser update for notifications on an object already queued this tick.
- Less directly: `UEdGraphSchema_K2::TryCreateConnection` marking the Blueprint modified (which also walks every K2
  node to clear cached data) per connection makes bulk graph edits slow (quadratic); a batched path, or a scope that
  defers the mark, would help tools.

## Workaround

Tools can connect with the base `UEdGraphSchema::TryCreateConnection` (when the response is
`CONNECT_RESPONSE_MAKE`) with the Blueprint's `bBeingCompiled` set for the call (so the node's default reset doesn't
mark it), set pin defaults with `bMarkAsModified = false`, and call `MarkBlueprintAsModified` once afterwards. In
our case that took a 44 GB spike to 34 MB and a 45 s build to 6 s. Setting `bBeingCompiled` from outside is a hack;
a supported way to defer the marks (a scope, or a `bCallModifyCallbacks` path through `TryCreateConnection`) would
be better.
